# 릴리스 글 직접 쓰기

릴리스 글의 절차는 실행기 지시서 하나가 정본이다. 직접 쓸 때도 그 절차를 그대로 밟고, HTTP 액션 대신 블로그 MCP 도구를 쓴다. 그래야 어드민에서 맡긴 글과 같은 기준·같은 단계 기록이 남는다.

## 시작

1. 지시서를 읽는다: `curl -sS https://blog.dongding.dev/api/releases/worker/` (토큰 없이 열린다). "단계별 할 일"과 "쓰기 기준"이 이 작업의 규칙이다. "순서"의 claim·report·finish 는 실행기 전용이라 건너뛴다.
2. `list_release_topics` 로 주제의 `stage` 와 `next` 를 본다. 요청이 지금 단계와 맞지 않으면(이미 점검까지 끝난 주제를 "처음부터" 등) 쓰기 전에 고르게 한다: 기존 초안 다듬기 / `update_release_topic` revert 로 되돌려 다시 쓰기 / 새 slug. revert 는 한 번에 한 단계만 내리고 그 단계의 근거만 지운다. 작업 노트·글·postSlug 는 남는다. revert 직전에 `stage` 를 다시 보고, 돌아온 `stage` 가 기대한 단계인지 확인한다. published 주제를 되돌리면 공개 글이 draft 로 내려가므로 서버가 막는다(사용자가 발행 취소를 말했을 때만 `unpublish: true`). 2026-10-12 review→draft 로 알고 부른 revert 가 발행된 ponytail 글을 내렸다.
3. `next` 단계부터 하나씩 한다. 단계를 건너뛰지 않는다.

주제가 어드민에서 **예약**된 것(`ai.status` queued, `ai.local` true)이면 release-reserved 로 집은 뒤 쓴다. 집지 않고 쓰면 어드민에는 계속 "예약"으로 남고 로컬 실행기가 같은 주제를 또 집는다.

## 대응표

| post_get | `get_post` |
| post_create | `create_post` (visibility `draft`) |
| post_update | `update_post` |
| check | `check_release_voice` |
| image | `upload_post_image` |
| (쓰기 기준) | `get_release_writing_guide` — 지시서 안의 기준과 같다. 주제 `kind` 가 `concept` 이면 `kind: "concept"` |

## 단계마다

- **2차 소스:** 공식 문서·PR·이슈를 읽고 확인한 사실에 링크를 단다. 직접 실행해 볼 수 있으면 해 보고 결과를 노트에 남긴다. **러닝 예시** 하나를 이때 정한다. 기준 독자가 이미 겪어 본 장면(결제 버튼을 두 번 누른 주문, 퇴사자 계정이 계속 부르는 API)이어야 하고, 그림·데모·활용 예를 모두 이 예시에서 가져온다. 활용 예 두세 개도 이때 찾는다. 공식 예제·샘플 저장소·문서 예시에서 러닝 예시와 이어지는 것을 고르고(README 에 실린 다른 저장소 예를 그대로 옮기지 않는다), 코드를 실행하지 않는 확인으로 직접 열어 본다. 예: Mods 글은 `claude-code-playground` 의 샘플 mod 셋을 받아 `claude plugin validate` 로 받는 이벤트·부르는 API 를 확인했다. 기준 독자(Claude Code는 쓰지만 이 기능은 처음 보는 개발자)가 이미 아는 것 한 줄과, 모를 용어를 한 문장 풀이와 함께 노트에 모은다.
  - 스킬·플러그인 전후를 `claude -p` 로 잴 때 로컬에서는 전역 CLAUDE.md 와 oh-my-claudecode·superpowers·ponytail 훅이 함께 실려 기준선이 오염된다. `--setting-sources project,local --strict-mcp-config` 에 `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` 로 띄우고 비교할 플러그인만 `--plugin-dir` 로 싣는다. 무엇이 실렸는지는 `--output-format stream-json --verbose` 첫 init 이벤트의 plugins·skills 와 훅 이벤트 수로 본다. 같은 문장으로는 스킬·MCP 도구가 안 불릴 수 있으니 실제 호출은 `tool_use` 이벤트로 본다(blog-capture 의 전·후 절). `--safe-mode` 는 `--plugin-dir` 의 훅까지 끈다. 말투·길이 스킬은 `output_tokens` 에 사고 토큰이 섞이니 `output_tokens_details.thinking_tokens` 로 나눠 본다. 조건과 횟수는 노트에만 적는다(2026-10-12 ponytail·caveman 글).
  - 처음 보는 CLI 를 돌려 볼 때는 전역 설치하지 않고 스크래치에 격리 설치한 뒤, 버전 확인 한 번까지 홈 디렉터리 기본값(`CODEX_HOME` 같은 환경변수)을 스크래치로 돌린 채 실행한다. 덮지 않으면 `--version` 만으로도 실제 홈에 임시 폴더가 생긴다. 소켓을 만드는 도구(데몬·서버)는 그 경로를 짧게 둔다. macOS 소켓 경로 한도가 104바이트라 scratchpad 경로 아래서는 소켓을 못 만들어 뜨지 않는다. 띄운 프로세스·사본·launchd 항목은 끝나면 지우고 `ps` 로 남은 것이 없는지 본다(2026-10-14 Codex 데몬 글).
- **자료:** 그림이 이 블로그의 차별점이다. **REQUIRED SUB-SKILL:** blog-figures 맨 앞 "그림이 글의 중심이다" 절을 따라, 글에서 이해가 막히는 지점(바뀐 동작·계산·순서·관계)마다 무엇을 그릴지 초안 전에 정하고 최대한 단순하게 그린다(그림 블록은 쓰기만 하면 스크롤 애니메이션이 붙는다). 실제 화면이 필요하면 **REQUIRED SUB-SKILL:** blog-capture.
  - 그림보다 먼저 **한 줄 결론·할 일·포맷**을 정한다(쓰기 기준의 "먼저 정할 것"과 "글 포맷"). 이해시키는 글은 설명형, 독자가 따라 설치·설정·사용하는 글은 가이드형이다. 제목과 요약 박스는 결론과 할 일에서 뽑고, 소제목은 답(평서문)으로 쓴다. 2026-10-13 "글이 뭘 말하고 싶은지, 시각자료가 도움이 되는지, 한눈에 읽히는지 모르겠다"는 지적에 시안(현재·설명형·전후 토글·가이드형)을 보이고 정했다.
  - 그다음 **뼈대와 핵심 장면**을 정한다. 쓰기 기준(`get_release_writing_guide`)의 "글 뼈대"에서 하나, blog-figures 의 "핵심 장면 고르기"에서 이 글에서 일어나는 움직임 동사 하나. `list_posts` 로 최근 글을 보고 같은 뼈대·같은 핵심 장면이 이어지지 않게 고른 뒤 노트 `## 자료` 첫 줄에 `한 줄 결론: … / 할 일: … / 포맷: 설명형|가이드형 / 뼈대: … / 핵심 장면: …(없으면 없음)` 을 적는다. 2026-10-11 그림이 든 11편이 전후 비교 → 터미널 장면 → 카드 셋 → 지원 표 순서로 굳어 "정해진 플롯과 애니메이션으로만 진행된다"는 지적을 받고 만든 절차다.
  - 장면(`scene: on`)은 순서가 곧 내용일 때만 그 동사로 만든다. 없어도 된다. 표·목록·숫자처럼 한 번에 다 보여야 하는 것은 장면으로 만들지 않는다. 같은 요청·설정의 전·후 화면은 이미지 묶음 `{tabs}` 로 싣는다. 그림은 지우면 막히는 곳에만, 글당 서너 개 안쪽. 토큰·값이 오가면 `data-spot`·`data-at`, 복사는 `from>to`, 설정 값을 바꾸면 터미널 diff, 칸이 차오르면 grid 장면, 버전마다 바뀐 것은 timeline, 계산은 bars. 터미널 화면 장면은 증거 자리라 유일한 장면이 되지 않게 한다(점검의 `scene-evidence-only`). 문법은 blog-figures 의 "장면".
  - 숫자가 주인공인 글(가격·성능)만 핵심 숫자 두세 개를 `stats` 카드로 모은다. 본문 숫자를 다시 모으는 카드는 두지 않는다.
  - 지금 키트로 그릴 수 없는 그림(새 화면 모양, 새 움직임)이 필요하면 흉내 내지 말고 **REQUIRED SUB-SKILL:** blog-figure-extend 로 키트를 더해 배포한 뒤 그 그림을 쓴다.
  - 스킬·플러그인·CLI 글은 실제 화면이 증거다. blog-capture 로 설치 화면, 예시 프롬프트의 실제 화면, 같은 요청을 도구 없이·있이 뜬 전·후 캡처를 이미지로 싣고 "조작 한 줄 → 캡처 → 결과 한 줄"로 잇는다. 태그가 skill·plugin 인 글은 실제 캡처가 두 장 미만이면 점검(`tool-no-capture`)에서 막힌다. 2026-10-12 "스킬을 설명할 땐 예시·방법·적용 전후·실제 스크린샷을 적극 쓰라"며 [참고 글](https://goddaehee.tistory.com/612)을 받았다.
  - 공개 저장소(GitHub 등)가 있는 도구는 설치 섹션 첫머리, 설치 명령 바로 위에 저장소 주소만 있는 줄을 앞뒤 빈 줄과 함께 둔다. 블로그가 링크 카드(북마크)로 펼친다(blog-mgmt MARKDOWN.md §8). 2026-10-14 "이런 스킬들은 가능하면 github 링크(북마크형태)로 본문에 넣도록" 요청.
  - 문장 속 링크에는 한 줄 설명을 단다: `[로컬 범위](https://… "이 폴더에서만 쓰도록 하는 등록")`. 블로그가 링크에 올리면 popover 로 띄운다. 30자 안팎, 괄호·큰따옴표 없이. 2026-10-14 "하이퍼링크를 걸 때는 설명을 popover 로, 최대한 간단하게 한 줄로" 요청.
  - 이 블로그의 다른 글을 가리킬 때 "…에서 다룹니다"·괄호 속 안내처럼 더 읽을 거리뿐인 링크는 문장에서 빼고 단락 바로 뒤에 `/posts/<slug>` 만 있는 줄로 글 카드를 띄운다. 낱말 뜻에 붙는 링크만 문장 안에 두고 한 줄 설명을 단다. 사이트 주소·`/preview/` 주소는 쓰지 않는다. 2026-10-14 다른 글을 가리킨 16곳이 전부 문장 속 링크라 "블로그 내부 글 레퍼런싱은 별도 렌더 언어가 있는데 활용하지 않는다"는 지적을 받았다.
  - 활용 예 두세 개는 실제 캡처가 있으면 캡처로, 없으면 blog-figures 의 "활용 예"대로 figure 장면의 터미널로 화면을 재현하고(문구는 직접 띄운 화면·README·소스에서 옮긴다, 캡처는 장면 안에 합친다, 어떻게 옮겼는지는 본문에도 캡션에도 쓰지 않는다), 따라 할 명령 한 줄로 맺는다. 이름·이벤트만 적은 카드로 끝내지 않는다.
- **초안:**
  - 개념 글(`kind: concept`, MVC·JWT 같은 개념 하나)은 지시서의 "개념 글일 때"를 따른다. 날짜·버전을 쓰지 않는다. 아래 배포일 규칙은 릴리스 글만.
  - 요약 박스는 두 문장, 160자 안팎. 첫 문장은 독자가 무엇을 할 수 있게 되는지, 버전·배포일은 둘째 문장에. 고칠 때는 문장을 덧붙이지 말고 있던 문장을 줄여서 맞추고, 고친 문장도 글자 수를 다시 잰다. 2026-10-08 Mods 글에서 독자 문장을 앞에 덧붙이기만 해 박스가 201자에서 237자로 늘었다.
  - 요약 박스에 버전마다 `v2.1.280(2026년 9월 23일 배포)` 를 붙인다. 날짜는 `released` 를 그대로 쓴다. 공식 발표일(미국 기준)과 하루 다르더라도 배포일 하나만 쓴다. 배포일 값이 없는 버전(글감이 아닌 이전 버전)은 요약 박스에 쓰지 않는다.
  - 제목은 쓰기 기준대로 짓는다. 주제 이름을 그대로 쓰지 않는다.
  - 본문 통째(`body`)는 처음 만들 때와 초안 단계에서 다시 쓸 때만 쓴다. 그 뒤 수정은 `replacements`.
  - 나란한 방법·선택지를 "첫째, 둘째, 셋째"로 한 문단에 잇지 않는다. blog-figures 의 figure 카드(`fig-grid-3`)로 나누고 문단에는 고르는 기준이나 용어 풀이만 남긴다. 점검이 `stock-phrase`(첫째·둘째로 잇는 나열 문단)로 잡는다.
  - 장황함을 걷어 낸다. 그림·표·장면이 보여 준 것은 문단에서 다시 풀지 않고, 용어 풀이는 괄호나 반 문장으로 붙인다. 다 쓴 뒤 문장마다 지워 보고 뜻이 통하면 지운다. 2026-10-08 JWT 글은 점검을 통과하고 읽기 6분이었는데도 "설명이 장황한 부분이 꽤 있다"는 지적을 받아 문단마다 한두 문장씩 줄였다.
  - 독자가 읽고 무엇을 하거나 고를 수 있는 것만 남긴다. 작업 기록(실행 환경·플래그·돌린 횟수·"확인하지 못했습니다"·"이 맥에"), 문서·절 번호·커뮤니티 반응을 주어로 세운 문장("RFC 6819 3.3절이 그대로 적습니다", "HN 스레드에서"), 이슈·PR 상태, 남의 벤치마크 세부, 제목 밖 릴리스 항목은 노트에 두거나 지운다. 짚은 문제에는 해법 코드·설정을 붙이고, 따라 칠 코드는 `opts` 로 가리지 않는다. 끝은 독자가 지금 할 일이다. 2026-10-12 최근 13편을 감사하니 13편 모두 근거를 주어로 세웠고 11편이 작업 기록을 본문에 남겨 "불필요하고 유익하지 않다, 예시도 직관적이지 않다"는 지적을 받았다. 점검이 `stock-phrase`(작업 기록·실행 환경 서술·근거를 주어로·커뮤니티 반응 인용)로 일부를 잡는다.
  - `create_post`·`update_post` 응답의 `report.stats.readTime` 이 6 이하인지 본다. 점검(`check_release_voice`)은 산문 4,000자만 보고 읽기 시간은 보지 않는다. 읽기 시간은 코드 블록의 단어와 링크 주소까지 세므로, 코드는 핵심 몇 줄만 남긴다.
- **점검:** `check_release_voice` 경고를 replacements 로 고쳐 다시 검사한다. 통과하면 `advance_release_topic`. 서버가 같은 기준으로 한 번 더 막는다.
  - `shape-repeat`(정보)는 최근 글과 그림 순서가 거의 같다는 뜻이다. 막지는 않지만, 뼈대나 핵심 장면 동사를 바꿀 수 있으면 바꾼다.
