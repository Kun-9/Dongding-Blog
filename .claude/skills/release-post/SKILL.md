# 릴리스 글 직접 쓰기

릴리스 글의 절차는 실행기 지시서 하나가 정본이다. 직접 쓸 때도 그 절차를 그대로 밟고, HTTP 액션 대신 블로그 MCP 도구를 쓴다. 그래야 어드민에서 맡긴 글과 같은 기준·같은 단계 기록이 남는다. 규칙이 왜 생겼는지(날짜 붙은 사고 기록)는 [HISTORY.md](HISTORY.md)에 있다. 규칙을 고치면 기록도 거기에 한 줄 더한다.

## 시작

1. 지시서를 읽는다: `curl -sS https://blog.dongding.dev/api/releases/worker/` (토큰 없이 열린다). "단계별 할 일"과 "쓰기 기준"이 이 작업의 규칙이다. "순서"의 claim·report·finish 는 실행기 전용이라 건너뛴다.
2. `list_release_topics` 로 주제의 `stage` 와 `next` 를 본다. 요청이 지금 단계와 맞지 않으면 쓰기 전에 고르게 한다: 기존 초안 다듬기 / `update_release_topic` revert 로 되돌려 다시 쓰기 / 새 slug. revert 는 한 번에 한 단계만 내리고 그 단계의 근거만 지운다. revert 직전에 `stage` 를 다시 보고 돌아온 `stage` 가 기대한 단계인지 확인한다. published 주제를 되돌리면 공개 글이 draft 로 내려가므로 서버가 막는다(사용자가 발행 취소를 말했을 때만 `unpublish: true`).
3. `next` 단계부터 하나씩 한다. 단계를 건너뛰지 않는다.

주제가 어드민에서 **예약**된 것(`ai.status` queued, `ai.local` true)이면 release-reserved 로 집은 뒤 쓴다. 집지 않고 쓰면 어드민에는 계속 "예약"으로 남고 로컬 실행기가 같은 주제를 또 집는다.

## 글의 모양 — 답부터

쓰기 기준의 "글 포맷"과 "글 뼈대"가 정본이다. 요약하면:

- 요약 박스(해당·문제·할 일, 릴리스면 넷째 줄 버전·배포일) 바로 아래 **첫 소제목이 해법**이다. 설정값·명령·코드·고르는 표·전·후 캡처 중 하나가 그 섹션에 있다. 사이에 문단·그림을 두지 않는다.
- 그다음 **왜 그런가** 섹션 하나~둘. 그림·장면은 여기. 소제목은 답(평서문).
- 일부 독자용 세부는 그 섹션 끝 접힌 칸 `> [!MORE] 누구에게 필요한지`(글당 셋, 칸마다 산문 600자). 아무의 할 일도 바꾸지 않는 사실은 노트.
- **끝 문단·'지금 해 볼 일' 목록 없음.** 할 일은 첫 섹션에 이미 있다.
- 본문 산문 1,500자 안팎(2,000자 넘으면 막힘), 장면은 하나에 3박자까지, 본문 코드는 핵심 열두 줄 안팎(16줄 넘으면 막힘, 전체는 접힌 칸).
- 가이드형은 첫 소제목이 설치·부르기(설치 명령 + 저장소 카드 + 예시 프롬프트 + 전·후 `{tabs}`), 활용 예는 한 섹션에 둘까지.

점검(`check_release_voice`)이 intro-paragraph·answer-late·closing-block·scene-long·code-long·heading-polite(합니다체 소제목)로 잡는다. 모범 글은 `get_post("access-refresh-token")`(설명형)과 `get_post("ponytail-skill-ladder")`(가이드형)이다. 새 글을 쓰기 전에 하나를 읽고 같은 모양을 목표로 한다.

다 쓴 뒤 문장마다 소리 내 읽어 어색한 문장과 생성 말투를 고친다. 점검의 `stock-phrase` 가 잡는 것(문두 그래서·즉·이는, ~한 것입니다, ~함으로써, 예고 문장, 나열 틀, 정의 틀, 홍보 형용사)은 일부다. 인접 문장의 주어 반복, 용어를 먼저 쓰고 다음 문장에서 푸는 뒤늦은 정의, 수치 문장의 보고 과거형("였습니다")은 점검이 못 잡으니 직접 본다.

## 단계마다

- **2차 소스:** 공식 문서·PR·이슈를 읽고 확인한 사실에 링크를 단다. 직접 실행해 볼 수 있으면 해 보고 결과를 노트에 남긴다. **러닝 예시** 하나를 이때 정한다(기준 독자가 이미 겪어 본 장면. 그림·데모·활용 예를 모두 여기서 가져온다). 활용 예 한두 개도 이때 찾는다(공식 예제·샘플에서 러닝 예시와 이어지는 것만, 코드를 실행하지 않는 확인으로 직접 열어 본다). 기준 독자가 이미 아는 것 한 줄과 모를 용어를 한 문장 풀이와 함께 노트에 모은다.
  - 스킬·플러그인 전후를 `claude -p` 로 잴 때는 `--setting-sources project,local --strict-mcp-config` 에 `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` 로 띄우고 비교할 플러그인만 `--plugin-dir` 로 싣는다(전역 CLAUDE.md·훅이 기준선을 오염시킨다). 무엇이 실렸는지는 `--output-format stream-json --verbose` 첫 init 이벤트로, 실제 호출은 `tool_use` 이벤트로 본다. `--safe-mode` 는 `--plugin-dir` 의 훅까지 끈다. 말투·길이 스킬은 `output_tokens_details.thinking_tokens` 를 나눠 본다. 조건과 횟수는 노트에만 적는다.
  - 처음 보는 CLI 는 스크래치에 격리 설치하고 홈 디렉터리 기본값(`CODEX_HOME` 등)을 스크래치로 돌린 채 실행한다. 소켓을 만드는 도구는 경로를 짧게(macOS 104바이트 한도). 띄운 프로세스·사본·launchd 항목은 끝나면 지우고 `ps` 로 확인한다.
- **자료:** 그림이 이 블로그의 차별점이다. **REQUIRED SUB-SKILL:** blog-figures 의 "그림이 글의 중심이다" 절을 따라, 이해가 막히는 지점마다 무엇을 그릴지 초안 전에 정하고 단순하게 그린다. 실제 화면이 필요하면 **REQUIRED SUB-SKILL:** blog-capture.
  - 그림보다 먼저 **해당·한 줄 결론·할 일·포맷**(설명형|가이드형)을 정하고, 사실을 본문·접힌 칸·노트 세 곳으로 가른다. 해당이 둘로 갈리면 글을 나눈다.
  - **뼈대와 핵심 장면**을 정한다. 쓰기 기준의 "글 뼈대"에서 하나, blog-figures 의 "핵심 장면 고르기"에서 움직임 동사 하나. `list_posts` 로 최근 글을 보고 같은 뼈대·같은 핵심 장면이 이어지지 않게 고른 뒤 노트 `## 자료` 첫 줄에 `해당: … / 한 줄 결론: … / 할 일: … / 포맷: … / 뼈대: … / 핵심 장면: …(없으면 없음)` 을 적는다.
  - 장면(`scene: on`)은 순서가 곧 내용일 때만, 글에 하나, 3박자까지. 표·목록·숫자처럼 한 번에 다 보여야 하는 것은 장면으로 만들지 않는다. 전·후 화면은 이미지 묶음 `{tabs}`. 그림은 지우면 막히는 곳에만, 글당 서너 개 안쪽. 터미널 화면 장면은 증거 자리라 유일한 장면이 되지 않게 한다(`scene-evidence-only`).
  - 숫자가 주인공인 글(가격·성능)만 핵심 숫자 두세 개를 `stats` 카드로 모은다.
  - 지금 키트로 그릴 수 없는 그림은 흉내 내지 말고 **REQUIRED SUB-SKILL:** blog-figure-extend 로 키트를 더해 배포한 뒤 쓴다.
  - 스킬·플러그인·CLI 글은 실제 화면이 증거다. 설치 화면, 예시 프롬프트의 실제 화면, 같은 요청을 도구 없이·있이 뜬 전·후 캡처를 "조작 한 줄 → 캡처 → 결과 한 줄"로 잇는다. 태그가 skill·plugin 인 글은 실제 캡처가 두 장 미만이면 `tool-no-capture` 로 막힌다. 눌러 보는 결과(위젯·인터랙티브 그림)는 PNG 가 아니라 ```embed 로 띄운다.
  - 공개 저장소가 있는 도구는 설치 명령 바로 위에 저장소 주소만 있는 줄(앞뒤 빈 줄)을 둔다. 링크 카드로 펼쳐진다(blog-mgmt MARKDOWN.md §8).
  - 문장 속 링크에는 한 줄 설명을 단다: `[로컬 범위](https://… "이 폴더에서만 쓰도록 하는 등록")`. 30자 안팎, 괄호·큰따옴표 없이.
  - 이 블로그의 다른 글은 문장 속 링크 `[문구](/posts/<slug> "그 글이 다루는 것")` 로 걸고, 더 읽을 거리면 그 단락 바로 뒤에 `/posts/<slug>` 카드 줄을 둔다. 카드만 두지 않는다(`card-unpaired`). 사이트 주소·`/preview/` 주소는 쓰지 않는다.
  - 버그·우회법 글은 그 버그가 고쳐지면 글 맨 위에 `> [!WARNING] 수정된 버그 · <수정일>` 박스를 단다. 같은 도구의 새 릴리스 글을 쓸 때 `list_posts` 로 그 도구의 버그 글을 찾아 고쳐졌는지 확인한다.
  - 활용 예는 실제 캡처가 있으면 캡처로, 없으면 blog-figures 의 "활용 예"대로 figure 장면의 터미널로 재현하고(문구는 실제 화면·README·소스에서 옮긴다, 어떻게 옮겼는지는 쓰지 않는다), 따라 할 명령 한 줄로 맺는다.
- **초안:**
  - 개념 글(`kind: concept`)은 지시서의 "개념 글일 때"를 따른다. 날짜·버전을 쓰지 않는다.
  - 요약 박스는 `> **해당** …`, `> **문제** …`, `> **할 일** …` 세 줄, 합쳐 160자 안팎. 명령·설정 이름은 할 일 줄에만. 버전·배포일은 넷째 줄 `v2.1.280(2026년 9월 23일 배포)`. 동작이 그 버전에서 시작됐을 때만 끝에 '부터'. 날짜는 `released` 그대로. 고칠 때는 덧붙이지 말고 있던 줄을 줄인다.
  - 제목은 쓰기 기준대로(독자의 증상·질문·얻는 것). 주제 이름을 그대로 쓰지 않는다.
  - 본문 통째(`body`)는 처음 만들 때와 초안 단계에서 다시 쓸 때, 구조를 바꿀 때만. 그 뒤 수정은 `replacements`.
  - 나란한 방법·선택지를 "첫째, 둘째"로 한 문단에 잇지 않는다. figure 카드(`fig-grid-3`)로 나누고 문단에는 고르는 기준만.
  - 장황함은 문장 압축이 아니라 실을 사실을 줄여서 걷어 낸다. 남긴 용어는 문장을 따로 세워 풀고 괄호에 몰지 않는다(한 문장에 새 용어 하나). 그림·표·장면이 보여 준 것은 문단에서 다시 풀지 않는다.
  - 독자가 읽고 무엇을 하거나 고를 수 있는 것만 남긴다. 작업 기록, 문서·절 번호·커뮤니티 반응을 주어로 세운 문장, 이슈·PR 상태, 남의 벤치마크 세부, 제목 밖 릴리스 항목은 노트에 두거나 지운다. 짚은 문제에는 해법 코드·설정을 붙이고, 따라 칠 코드는 `opts` 로 가리지 않는다.
  - 다 쓴 뒤 문장마다 소리 내 읽어 번역투·생성 말투를 걷어 낸다('즉,'·'다시 말해'·'물론'·'참고로'·'또한'·'이는', '~함으로써'·'~에 있어'·'~로 인해'·'~뿐만 아니라'·'~라는 점입니다'·'~에 도움이 됩니다', 홍보 형용사, 긴 관형절 중첩, 주어와 서술어가 어긋난 문장). 점검의 `stock-phrase` 가 일부를 잡지만 전부는 아니다.
  - `create_post`·`update_post` 응답의 `report.stats.readTime` 이 3 이하인지 본다. 읽기 시간은 코드 블록의 단어와 링크 주소까지 세므로 코드는 핵심 몇 줄만 남긴다.
- **점검:** `check_release_voice` 경고를 replacements 로 고쳐 다시 검사한다. 통과하면 `advance_release_topic`. 서버가 같은 기준으로 한 번 더 막는다.
  - `shape-repeat`(정보)는 최근 글과 그림 순서가 거의 같다는 뜻이다. 뼈대나 핵심 장면 동사를 바꿀 수 있으면 바꾼다.
  - 문체 점검은 사실을 보지 않는다. "미확인", "문서에 없음", "초안"으로 적은 사실은 공식 문서를 다시 찾고, 여러 언어·도구로 넓혀 말한 문장은 확인한 범위로 좁힌다.
  - advance 전에 모바일에서 본다: `node .claude/skills/release-post/mobile-check.mjs <slug>`. 운영 미리보기에 `.env.local` 스튜디오 계정으로 로그인해 390px 라이트·다크로 끝까지 내리며 가로 넘침, 판 밖 요소, 토큰 중간 줄바꿈, 겹친 단계 화면, 화면보다 큰 무대, 말줄임으로 잘린 글자, 칸 밖으로 삐져나온 글자를 잡는다. 끝 코드 0 통과, 1 문제 목록(글 쪽이면 replacements 로, 렌더러 쪽이면 사용자에게 알리고 코드는 워크트리에서), 3 브라우저·로그인 불가(finish 의 `todo` 에 "모바일 확인"). `figures` 가 0이면 미리보기를 못 본 것이다. 검사가 통과해도 `--shots <폴더>` 의 박자 사진을 눈으로 본다.
  - 데스크톱 첫 화면도 본다: `node .claude/skills/release-post/skim-check.mjs <slug> <폴더>`. `00.png` 에서 제목·요약 박스·첫 소제목만으로 자기 일인지와 할 일이 읽히는지, `headings` 만 이어 읽어도 답이 이어지는지 본다. draft 도 된다.
