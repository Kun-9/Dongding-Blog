# 예약된 릴리스 글 쓰기

어드민에서 "AI에게 맡기기"의 실행 칸을 **예약**으로 고른 주제는 클라우드 루틴이 집지 않고 로컬 세션을 기다린다. 이 스킬은 그 목록을 보여 주고, 사용자가 고른 하나를 집어 release-post 절차로 쓴다.

## 1. 조회

블로그 MCP `list_release_topics` 를 `reserved: true` 로 부른다. 예약된 주제만 온다(`ai.status` queued, `ai.local` true).

비어 있으면 "예약된 글이 없습니다" 한 줄과, 어드민(https://blog.dongding.dev/admin/releases)에서 맡기기의 실행 칸을 "예약"으로 고르면 여기 쌓인다는 안내로 끝낸다.

## 2. 리스트업

맡긴 순서(`ai.updatedAt` 오래된 것부터)로 표를 보여 준다.

| 열 | 값 |
| --- | --- |
| 번호 | 1부터 |
| 제목 | `title` |
| 범위 | `next.label` → `ai.until` 라벨 (sources 2차 소스, assets 자료, draft 초안, review 점검) |
| 종류 | `kind` — release 릴리스, concept 개념 |
| 맡긴 시각 | `ai.updatedAt` 을 한국 시각 `MM.DD HH:mm` |

표 아래에 주제마다 `angle` 한 줄을 붙인다. 다른 설명은 덧붙이지 않는다.

## 3. 선택

AskUserQuestion 으로 고르게 한다. 하나뿐이어도 묻는다 — 집는 순간 어드민에 "작성 중"으로 바뀌기 때문이다.

- 1개: "이 주제 쓰기" / "그만두기" 두 선택지.
- 2~4개: 주제마다 선택지 하나(label 은 제목, description 은 범위·종류).
- 5개 이상: 오래된 4개를 선택지로 두고, 나머지는 Other 에 번호나 제목으로 받는다.

## 4. 집기

`claim_release_work` 를 고른 주제의 `id` 로 부른다. 주제가 running 이 되고 어드민 "AI 작성 중" 구역에 실시간 로그로 보인다. 돌아온 `work` 가 이후 작업의 기준이다.

`work` 가 null 이면 그 사이 다른 세션이 집었거나 어드민에서 취소한 것이다. 그렇게 알리고 1번부터 다시 한다.

집기 호출이 응답 없이 끊겼으면(사용자 중단·네트워크 오류) 요청은 서버에 닿아 집혔을 수 있다. 같은 `id` 로 다시 부른다 — 집은 뒤 진행 기록이 없으면 그 주제가 그대로 온다. 집기를 다른 세션(서브에이전트)에 넘길 때도 그쪽이 같은 `id` 로 부르면 된다. (기록: release-post/HISTORY.md).

진행 기록이 쌓인 채 멈춘 running 주제(세션이 끊긴 것)는 다시 집지 않는다. 2시간 안이면 null 이 오고, 넘으면 진행 로그를 지우고 처음부터 집힌다. 이어 받는 쪽은 `report_release_work` 로 시작하고(running 이면 받아 준다), 노트·`get_post` 로 어디까지 했는지 본 뒤 `next` 단계부터 잇는다.

## 5. 쓰기

**REQUIRED SUB-SKILL:** release-post 로 쓴다. 다만 이 주제는 집은 작업이라, release-post 가 실행기 몫이라며 건너뛰는 claim·report·finish 를 여기서는 한다.

- **범위:** `next` 단계부터 `ai.until` 까지만. until 을 넘기지 않는다. 더 하고 싶으면 끝낸 뒤 사용자에게 묻는다.
- **보고:** 단계를 시작할 때와 작은 일마다 `report_release_work` 로 한 줄 상황을 남긴다(1~2분에 한 번, "공식 문서 읽는 중 — …", "흐름 그림 그리는 중"처럼 구체적으로). 에러가 나면 먼저 사이트가 살아 있는지 본다(`curl -sI https://blog.dongding.dev/`). 402·5xx 면 사이트가 내려간 것이라 서버 쓰기 직전까지 스크래치에서 준비하고 사용자에게 알린다. 사이트가 멀쩡한데 에러면 어드민에서 취소한 것이니 즉시 멈추고 finish 도 부르지 않는다.
- **끝내기:** 마지막에 반드시 `finish_release_work`. 성공이면 ok=true 와 한두 줄 요약, 막혔으면 ok=false 와 막힌 이유. 사람 몫의 남은 일(끝내 못 뜬 캡처, 미확인 사실 등)은 `todo` 에 한 줄로.
- **끝낸 뒤 고칠 때:** finish 뒤에 노트나 글을 또 고치면 맨 마지막에 같은 `todo` 로 finish 를 한 번 더 부른다. 어드민의 "남은 일"은 마지막 finish 뒤 주제가 바뀌면 빈다. 끝난 주제는 running 이 아니라 `report_release_work` 가 에러를 내니 부르지 않는다.
- **중단:** 사용자가 도중에 그만두라고 하면 finish ok=false 로 "사용자가 중단"과 어디까지 했는지를 남긴다. 집은 채 두면 어드민에 2시간 동안 "작성 중"으로 남는다.

## 여럿을 맡을 때

사용자가 여러 개("3개씩", "남은 거 다")를 맡기면 주제마다 서브에이전트 하나에 맡기고 메인은 보고만 받는다.

- **공통 규칙은 파일 하나.** 집필용·검토용 규칙을 스크래치에 한 번 쓰고, 프롬프트에는 주제마다 다른 것(주제·러닝 예시 후보·겹치는 글·주제 전용 안전 조건)만 적는다. 같은 묶음끼리 뼈대·핵심 장면·러닝 예시 도메인을 미리 나눈다.
- **글마다 독립 검토.** 글쓴이가 finish 하면 검토 에이전트를 따로 띄운다. 블로그 쓰기 도구와 모델을 부르는 재측정은 쓰지 않고 읽기·재현만 한다. 목록은 먼저 파일로 쓰고(세션이 끊겨도 남게) SendMessage 로 글쓴이에게 보낸다. 글쓴이가 없으면 반영 에이전트가 그 파일만 보고 반영한다. 반영 뒤에는 위 "끝낸 뒤 고칠 때"대로 finish 를 다시 부른다. 32편에서 검토마다 10~20개가 나왔고, 대부분 잰 범위를 넘긴 문장과 빠진 다음 할 일이었다.
- **사용자에게는** 글마다 끝난 단계·사람 몫과 검토의 가장 심각한 셋만 알린다.
- **끊겼을 때.** 사용 한도에 걸린 에이전트는 해제 뒤 SendMessage 로 멈춘 자리부터 잇게 한다. 세션이 다시 시작되거나 재부팅으로 에이전트와 스크래치(`/tmp`)가 사라지면 어드민 로그·노트·글이 기준이다. running 으로 남은 주제는 위 4번 끝 문단대로 이어 받고, 검토 목록 파일이 사라진 글은 다시 검토한다.
- **시험 안전**은 release-post "2차 소스"의 시험 항목을 그대로 따른다. 사용자 폴더(`~/.claude`, `~/.agents`)의 수정 시각을 시작 전에 적어 두고 끝나면 대조한다.

## 끝

- release-post 의 "끝" 조건을 채웠고, `finish_release_work` 를 불렀다.
- 사용자에게 끝낸 단계, 초안 미리보기(`https://blog.dongding.dev/studio`), 남은 일을 알린다.
- 예약이 더 남았으면 몇 개인지 알리고, 이어서 고를지 3번처럼 묻는다.
