## 들어가며 — 작성-검증을 같은 세션에서 하지 않는다

AI 작업의 함정은 *말로는 다 됐는데 실제로는 안 되어 있는* 상황입니다. 이건 AI의 잘못이라기보다 *"확인 안 한 사람의 잘못"* 입니다. 그래서 모든 작업에 검증 게이트를 박았습니다.

코드를 쓴 세션이 자기 검증을 하면 *"잘 됐어요"* 가 나오기 쉽습니다. 자기가 쓴 글의 오타를 자기가 잘 못 찾는 것과 같은 원리입니다. 새 컨텍스트의 reviewer 에이전트가 따로 봅니다.

## 1. 4단 게이트

| 단계 | 도구 | 잡아내는 것 |
|------|------|------------|
| 1. 빌드 | `npm run build` | 컴파일 에러, import 깨짐 |
| 2. 린트 | `npm run lint` | 코딩 컨벤션 위반 |
| 3. 타입체크 | `tsc --noEmit` | 타입 시스템 위반 |
| 4. 브라우저 실측 | 직접 클릭 / 스크린샷 회귀 | hydration 에러, 시각 디테일, 빈 상태 |

빌드가 통과해도 브라우저에서 안 도는 경우가 흔합니다. 특히 hydration 에러는 빌드가 잡아주지 못합니다. `tmp/dev-check/home-after-fix.png` 가 그 증거입니다 — 빌드는 통과했지만 실제 화면이 깨져 한 번 보정한 흔적입니다.

### 실제로 잡힌 환각

카테고리 데이터를 갱신하면서 AI가 *"`getCategoryBySlug`라는 헬퍼를 사용 중입니다"* 라고 보고했는데, 실제 코드엔 그런 함수가 없었습니다. 새 reviewer 세션이 grep으로 즉시 잡았습니다. 같은 세션이었으면 못 잡았을 환각입니다.

> [!NOTE] 검증의 원칙
> 셀프 검증은 검증이 아닙니다. 작성한 사람과 확인하는 사람은 달라야 합니다 — 그 사람이 사람이든 에이전트든 마찬가지입니다.

## 2. split-commit 으로 의미 단위 커밋

AI는 한 번에 너무 많은 일을 합니다. 시키는 대로 두면 *"파일 32개 변경된 거대한 한 커밋"* 이 나오고, 나중에 추적이 불가능해집니다.

`split-commit` 흐름으로 변경을 기능별로 나눠 여러 커밋을 만듭니다. 이 블로그의 최근 커밋 히스토리는 그 결과물입니다.

```
[DOCS] site — 이메일 갱신·rss 비활성화
[REFACTOR] Admin — 헤더/초안 섹션의 CTA 제거
[REFACTOR] Header — admin 글리프를 bar-chart svg로 교체
[FEAT] Studio — 이미지 업로드·취소 다이얼로그·callout 4종 분리
[FEAT] 카테고리 — 서브카테고리 라우팅·헬퍼·데이터 갱신
```

`태그 + 영역 + 짧은 설명` — `[FEAT] / [REFACTOR] / [DOCS] / [FIX]` 컨벤션을 운영 문서에 한 번 박아두면 *"커밋해줘"* 한 마디로 자동 적용됩니다.

> [!TIP] 이 단계에서 사용한 스킬
> - `code-reviewer` — 새 컨텍스트의 코드 리뷰 에이전트
> - `verifier` — 작업 완료 주장의 증거 기반 검증
> - `split-commit` — 변경사항을 의미 단위로 분리
> - `qa-commit` — QA 컨벤션(`[QA-번호]`) 강제

## 3. 회고 — 다음 프로젝트로 가져갈 5가지 패턴

5단계 일지 전체를 닫으며, 다음 프로젝트로 가져갈 패턴을 정리합니다.

1. **기획·설계가 끝나기 전엔 코드 한 줄도 쓰지 않는다.**
2. **디자인 토큰부터 정의한다.** 시안은 그 위에서만 그린다.
3. **메인 세션은 지휘자, 손은 sub-agent.** 컨텍스트는 보호 자원이다.
4. **검증은 다른 세션에서.** 셀프 검증은 검증이 아니다.
5. **변경은 의미 단위로 쪼개 커밋한다.** 거대한 한 커밋은 미래의 자기를 괴롭힌다.

## 닫으며 — 시리즈를 닫으며

블로그 한 채를 AI와 함께 짓고 나서, *"AI에게 일을 시키는 법"* 보다 *"AI를 운영하는 시스템을 만드는 법"* 이 더 중요하다는 결론에 도달했습니다. 도구는 수단이고, 운영 모델이 결과의 질을 결정합니다.

그 운영 모델의 가장 단단한 뼈대는 — **순서를 지키는 것** 이었습니다. 기획이 디자인보다 먼저, 디자인 시스템이 시안보다 먼저, 시안이 코드보다 먼저, 검증이 배포보다 먼저.

이 5단계 시리즈가 누군가의 시간을 줄여줄 수 있다면, 그것으로 충분히 기쁠 것 같습니다.
